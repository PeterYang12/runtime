# E2B single-node benchmark on AMD EPYC

Performance tests of the self-hosted E2B stack (`../embed/compose`) on one
AMD EPYC server, structured after the CubeSandbox
[CubeBench v0.7.3 report](https://cubesandbox.com/blog/posts/2026-10-28-cubebench-073)
so the results read side by side with it.


## Layout

| Path | What |
|---|---|
| `bench.py` | the tests, one subcommand per report section |
| `run.sh` | runs `bench.py` with the SDK settings of the local compose stack |
| `.venv/` | Python env with `e2b==2.46.0` (the SDK version Embed is tested with) |
| `report.py` | builds `REPORT.md` from the pinned runs (`RUNS`), in the CubeBench report format |
| `REPORT.md` | the report (English), generated by `report.py` |
| `results/<UTC time>-<test>/` | one directory per run: `env.md`, `raw.jsonl`, `summary.json`, `summary.md` |

## Test plan (mirrors CubeBench sections)

| Section | Test | Subcommand | Status |
|---|---|---|---|
| 2 | Test environment | `env` | done |
| 3.2 | Cold start and concurrency scaling (1, 10, 20, 50, 100, 200) | `create` | done |
| 3.3 | Single-host density (0 to 200 idle sandboxes) | `density` | done |
| 4.1 | Snapshot creation vs concurrency (1, 5, 10) | `snapshot` | done |
| 4.2 | Snapshot creation vs dirty memory (0 to 1024 MiB) | `snapshot-dirty` | done |
| 4.3 | Create from snapshot (1, 10, 20, 50) | `from-snapshot` | done |
| 4.4 | Rollback | n/a | E2B has no rollback API; 4.3 covers recreate-from-snapshot |
| 4.5 | Clone (fork 1, 10, 100) | `fork` | done |
| 4.6 | Pause / resume (1, 5, 10) | `pause` | done |

Main sandbox spec: a `swesmith-*` template (2 vCPU / 2048 MiB), the size the
RL jobs use and close to CubeBench's 2 vCPU / 2000 MiB. `base` (512 MiB) is
run once in 3.2 as a platform reference.

## Usage

```bash
./run.sh env
./run.sh create --template swesmith-090a7c94c767-m2
./run.sh create --template base --levels 1,10,20,50 --rounds 3
```

`create` refuses to start while other sandboxes run on the node, and waits
after every round until the node is idle again (no sandbox, hugepages back).

## Definitions

- **ready**: from sending the create request to the first command (`true`)
  finishing inside the sandbox; what a user actually waits for.
- **api**: from sending the create request to the API answering.
- **wall**: one round, first request sent to last sandbox ready.
- **throughput**: successful sandboxes per round / average wall time.
- **start-limit rejections**: `ResourceExhausted` the orchestrator logged;
  it admits at most 3 starts at once (`max-starting-instances-per-node`) and
  the api retries the rest, so these are retries, not client errors.
- **steal**: CPU time the hypervisor of this droplet took away.

## Caveats for comparing with CubeBench

- CubeBench ran on a 96-vCPU Intel Xeon bare-metal host with local NVMe;
  this is a 64-vCPU AMD EPYC DigitalOcean droplet (sandboxes run nested) with
  templates on a network block volume. The numbers are context, not a
  head-to-head CPU comparison.
- E2B caps a node at 200 running sandboxes and 3 concurrent starts.
- The client runs on the same host, so it shares the CPU with the sandboxes.
